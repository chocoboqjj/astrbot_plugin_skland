## 项目分析：astrbot_plugin_skland

通读了插件全部源码（main.py 421行 / skland_api.py 616 行），确认作用与结构：

- 本质是给 AstrBot 写的**森空岛自动签到插件**（v1.4.0，作者 Azincc），由 Rust 版Skland-Auto-Sign-In 移植而来，核心难点在设备指纹伪装 + 请求签名。
- `skland_api.py`：协议层。设备 dId 生成（RSA 加密 UUID、24 字段 DES 混淆表 tn 校验、gzip + AES-128-CBC 上报 fp-it.portal101.cn），后续按 `grant → cred → binding → attendance` 四步换取并签名调用；签名 = HMAC-SHA256 后再 MD5，方舟与终末地端点不同，终末地按 `sk-game-role` 头逐角色循环。
- `main.py`：AstrBot 调度层。5 个指令（skdhelp/skdlogin/skdlogout/skdusers/skd）+ APScheduler 每日定时签到 + KV 存储 users/groups 落库。
- 双游戏支持（明日方舟 appCode=arknights、终末地=endfield），终末地支持一人多号。

### 已发现的代码问题（未修改，仅记录待用户确认）

1. `main.py:389` 昵称回写用 `put_kv_data("users", {..., user_id: {"last_username": nickname}})`，**整体覆盖该用户记录**，会把 token、umo、last_sign 等字段全部丢掉。属严重数据丢失 bug，且与同函数末尾的`users_data[uid] = user_data` 逻辑冲突。
2. `main.py:386` `if user_id in str(users_data.get("umo"))` 判断写错，疑似应为 `str(user_data.get("umo"))`，导致昵称更新分支几乎不会正确命中。
3. `main.py` 第 407 行裸`except:` 吞掉所有异常，无日志。
4. `skland_api.py` 中 import 顺序不规范（`logger = logging.getLogger` 夹在 import 中间）；logger 用标准 logging 而非 AstrBot logger，日志不会进 AstrBot 日志系统。
5. `_conf_schema.json` 默认值与 `main.py:_init_config` 的 `put_config` 默认值冲突：auto_sign_enabled false/true、auto_sign_hour 9/1。
6. `/skd` 群聊模式对每个群成员都串行跑一次完整鉴权链（4~5 次 HTTP），人数多时很慢且请求量大。
7. token 明文存 AstrBot KV，等同密码；且 `skdlogin` 群聊拦截只提示撤回，未自动撤回消息。

`AGENTS.md` 内容是 Rust 项目的规范（cargo build 等），与实际 Python 插件不符，属于文档遗留，未清理。

## 接入 QQ 官方机器人的可行性分析（仅分析，未改代码）

### 平台能力调研结论（2026-10-20 当日核实）

QQ 官方机器人（qq_official）相比 OneBot/NapCat 的关键限制：

1. **主动推送已被官方取消**（2025-04-21 公告）。后续「残缺版」下放：群聊需群主在手机端手动开启「允许主动在群聊内发言」且**默认关闭**；单聊仅在用户先发过消息后，按当天/1-3天/3-7天/7-30天四个周期各下发 1 条召回消息，**总计 4 条封顶**。
2. **被动回复窗口 5 分钟**，每条消息最多回复 5 次。
3. **群聊必须 @ 机器人**才能触发指令。
4. **AstrBot 适配器限制**：qq_official 只实现了 `on_group_at_message_create`，**没有实现 `on_group_message_create`**，即使 QQ 推送了全量群消息 AstrBot 也会静默丢弃（GitHub issue #8131，2026-05 仍未修复）。需@机器人触发。
5. 沙箱环境最多 20 人；正式环境需 IP 白名单；**只能被加到自己为群主的群**。
6. 用户 ID 体系不同：单聊用 openid（非 QQ 号），群用 group_openid，**与 OneBot 的 QQ 号不通用**。

### 结论

插件**核心卖点「每日定时私发签到结果」在 QQ 官方平台上不可行**，这是产品级冲突，不是改几行代码能绕过的。

### 推荐方案：推送模型 → 拉取模型

- 定时任务仍按时执行签到，但**结果只落库不推送**（`user_data["last_result"]`）
- 用户主动发 `/skd` 时读库渲染，附「上次签到时间」
- 群聊汇总改为可选增强：群主开启主动发言开关后，每日群内播报一次小结，失败静默降级
- 额外收益：顺带解决原 `/skd` 群聊每次都跑完整鉴权链的性能问题

### 代码改造点定位

- `main.py:180 _send_private_message` — 整块需重设计（阻塞点）
- `main.py:232 / 286 / 339 / 362` 的 `getattr(event.message_obj, "group_id", None)` — 应改用 `@filter.event_message_type(...)` 装饰器
- `main.py:357 skd` 群聊分支 — 遍历逻辑重写，groups key 需按 platform_name 隔离
- `main.py:269` 存 `umo` 当推送地址 — 官方平台下语义失效
- `main.py:241` users 主键 — openid 与 QQ 号不通用，同一用户跨平台会分裂成两条记录，token 需支持多平台绑定
- `skland_api.py` — **完全不用改**，签到走森空岛接口与 QQ 平台无关

## Bug 修复：QQ 官方群里 @机器人 发送 skd 无反应

### 根因（已通过阅读 AstrBot 源码 + 复现脚本确认）

链路三段：
1. `qqofficial_platform_adapter._parse_from_qqofficial` —— 会用 `_strip_bot_mention_markup` **剥离** @ 标记，所以 `message_str` 变成 `skd` 而不是 `<qqbot-at-user/>skd`

3. `star/filter/command.py:191-206` —— `CommandFilter` 要求剥前缀后**全等匹配**指令名，此时拿到空串 → 匹配失败

结论：AstrBot 指令默认必须带 `/` 前缀。`@机器人 skd` 不带斜杠必然无响应。

## 新增：森空岛接口日志（含敏感字段脱敏）

用户要求「把森空岛接口返回的值也 log 出来」。

### 实现
在 `skland_api.py` 的 `_request` 里统一打点 —— 所有接口都走这里，一处改动全覆盖：
- `_log_request()`：请求方法、URL、请求体、请求头（仅首次尝试时打，避免重试刷屏）
- `_log_response()`：HTTP 状态码、尝试次数、原始响应体（超过 2000 字符截断）
- 请求失败时 warning 级别打印重试信息

顺带把终末地签到从裸 `client.post` 改为走 `_request`，统一日志与重试逻辑（签名用的 body 仍是空串，与 httpx `json=None` 一致，不影响签名校验）。

### 脱敏设计（关键）

`_mask()` 递归脱敏，保留首尾各 4 位。**难点在于同名字段含义不同**：
- 顶层 `code` 是接口状态码（0 = 成功）→ **必须保留**，否则无法排查成败
- `data.code` 是 oauth 授权码 → 需脱敏
- `data` 本身通常是业务数据 → 不脱敏（奖励列表、绑定列表等要能看到）

实现上用 `parent_key` 追踪父级键名做路径判定：仅当 `k == "code" and parent_key == "data"` 时脱敏。

`_SENSITIVE_KEYS` = token / cred / sign / dId / ep / content / deviceId / authorization / password / secret

```python
f"/v2/groups/{group_id}/messages/{message_id}", group_openid=group_id, message_id=message_id
```
查 botpy 源码（github.com/tencent-connect/botpy）确认 `Route.url` 的实现：
```python
_url = _url.format_map(self.parameters)
```
`format_map` 只替换路径中存在的占位符，多余 kwargs 被忽略。原写法虽能生成正确 URL（f-string 已是最终值），
但 kwargs 里的 `group_openid` 找不到对应占位符，属无效参数。

已改为官方适配器的标准形式（占位符 + kwargs）：
```python
Route("DELETE", "/v2/groups/{group_openid}/messages/{message_id}",
      group_openid=group_openid, message_id=message_id)
```

**2. 参数来源核验（都正确）**
- `group_openid`：`event.message_obj.group_id` 在官方适配器里就是 `message.group_openid`
  （`qqofficial_platform_adapter.py`: `abm.group_id = cast(str, message.group_openid)`）
- `message_id`：`abm.message_id = message.id`，正是文档所说「群成员的消息ID从群消息事件 d.id 获取」

**3. 域名确认**
`Route.DOMAIN = "api.sgroup.qq.com"`，官方适配器发群消息（`post_group_message`）用的是**同一个 Route 类**，
所以撤回与发消息走同一套域名与鉴权，无需特殊处理。

**4. 错误码映射增强**
新增 `_RECALL_ERROR_HINTS`，把文档的 4 个错误码映射为用户可读提示：
- `40062003` → 机器人不是群管理员，无权撤回他人消息
- `40064004` → 消息发送已超过 2 分钟，官方接口不允许撤回
- `40061001` → 请求参数无效
- `50065001` → 撤回失败，请稍后重试

`_recall_message` 返回值改为 `(bool, str)`（成功标志 + 失败原因），群里提示相应调整。

**关键认知**：机器人在群里是**普通成员**时只能撤回自己发的消息，撤不掉用户发的。
这意味着群聊撤回功能**强依赖机器人是群管理员**。

## 三项修复：名字溢出 / 奖励显示 / 签到请求时机

### 1. 多账号名字溢出画布

**根因**：原来按**字符数**截断（`ak_name[:20]`），但中文与英文像素宽度差异大，
多账号名字累加后超出画布（双游戏时名字起点在 x=342，仅剩 334px）。

**修复**：新增 `_ellipsize(d, text, max_px, size, bold)` —— 按**实际像素宽度**截断，
逐字符裁剪直到能放下省略号。`max_px = W - PAD - x` 动态计算。

### 2. 奖励重新显示（换行、不对齐、两游戏分隔）

- 图片卡片：奖励**另起一行**（`AWARD_H = 26`），缩进对齐到游戏名列，
  两个游戏的奖励用 `｜` 分隔
- 画布高度：`H = 150 + base_rows * ROW + award_rows * AWARD_H + 62`
- 补回 `ak_awards` / `ef_awards` 字段到群聊 rows 与私聊 rows

### 3. 签到请求时机

**关键洞察**：`last_sign` 存的是**日期字符串**（如 "2026-10-20"），跨天自然不相等，
因此**每日 0 点自动重置**是天然实现的，不需要额外的重置任务。

新增 `_account_signed_today(account, today)`，在以下两处跳过已签到的账号：
- 群聊 `/skd` 的 live 分支
- 定时自动签到任务

`auto_sign_hour` 默认值从 9 改为 **0**（配合「每日 0 点重置并签到」的语义），
`_conf_schema.json` 同步更新。

### 顺带修的 bug：单账号失败导致整行隐藏
原来任一账号请求失败就 `failed = True`，该用户的**所有账号**都不显示。
改为：只有「需要查询的账号全部失败」**且**「没有任何账号有有效签到结果」时才标记失败。

### 验证

### 追加：签到时间拆分为「状态重置」与「执行」两个时间

用户澄清：**状态重置在每天 0 点，签到执行在每天 0:30**。

## 重复账号：跨平台登录未归一

用户反馈「有重复录入的账号」。

### 根因
`alias` 字段**只有读取逻辑（`_resolve_user_key`），没有任何地方写入**。
同一个人从 OneBot（QQ 号）和 QQ 官方（openid）分别登录时，
`event.get_sender_id()` 返回的值不同 → 产生**两条独立的 users 记录**，
各持一份相同 token → 签到列表出现重复。

### 修复
新增 3 个方法：
- `_find_user_by_token(users, token, exclude)` —— 在所有用户记录中查找持有该 token 的用户
- `_merge_user_account(users, target_id, source_id, account)` —— 合并两条记录：
  平台绑定（umo_by_platform）取并集、账号列表按 token 去重、删除 source 记录
- `/skdmerge` 指令（仅管理员）—— 检测并合并存量重复数据

`skdlogin` 里在写入前检测重复，命中则自动合并（保留当前登录用户为主记录），
回复中提示「🔗 检测到该账号已在其他平台绑定，已自动合并重复记录」。
群成员列表里的旧用户键也同步替换。

### 顺带修的两个 bug
1. `_upsert_account(target, {})` 传空账号时，token 为 None 会**追加一个空账号** →
   改为 token 为空时直接返回，不写入
2. `_merge_user_account` 在目标用户不存在时直接 return 不合并 →
   改为以 source 为基础新建 target

### 验证
新增 6 组重复账号专项测试（检出跨平台重复 / exclude 生效 / 合并后无重复账号 /
平台绑定保留 / skdmerge 清理存量 / 非管理员拦截），**十八套测试总计 0 失败**。

### 追加：登录两次产生重复的两个真实根因

用户澄清：「理论上已经绑定过的账号除非登录应该不能再绑定，现在就是有人 login 了两次出现重复」。

**根因 1：token 未规范化（最隐蔽）**
原来只用 `.strip()`。用户在 QQ 复制粘贴 token 时常混入**不可见字符**：
零宽空格 U+200B、零宽连接符 U+200D、BOM U+FEFF、方向标记 U+202A-U+202E、
全角空格 U+3000 等 —— 这些让 `str.strip()` 无效（`\u200b.isspace()` 是 False），
于是同一个 token 被当成两个不同账号。

修复：新增 `_normalize_token()`，剔除上述隐形字符 + 去掉所有 `isspace()` 空白。

**根因 2：跨平台登录未归一**
`alias` 字段**只有读取逻辑（`_resolve_user_key`），没有任何地方写入**。
同一人从 OneBot（QQ号）和 QQ官方（openid）分别登录 → `get_sender_id()` 不同
→ 产生两条独立 users 记录，各持一份相同 token。

修复：`_find_user_by_token(users, token, exclude="")` **全局**查 token 持有者，
登录时若命中其他记录就**复用**它（不再新建、不再合并），并为当前 sender_id
建立一条轻量**别名记录**（只有 `alias` 字段、无 token），使
`_resolve_user_key` 能解析回主记录。

**配套改动**：
- 新增 `_count_real_users(users)` —— 排除别名记录，所有用户数统计改用它
- 群成员列表统一存**主记录键**（`_resolve_user_key` 解析后），与 `_find_user_groups` 口径一致
- 签到名单遍历跳过无账号的别名记录

**验证**：新增 5 组专项测试（token 规范化 8 种隐形字符 / 同平台登录两次 /
跨平台登录复用 / 别名记录不计入 / 不同 token 不误合并），**十九套测试总计 0 失败**。

### 追加：/skdmerge 能清理存量重复（含脏 token 场景）

用户问「目前已经重复的能清理吗」。发现原 `/skdmerge` 有漏洞：
**按精确 token 匹配** → 而重复很可能正是脏 token 造成的，规范化后能匹配、精确匹配匹配不到。

**修复**：
1. `/skdmerge` 归组改用**规范化后的 token**
2. 顺带把脏 token 规范化写回（新增 `_normalize_accounts_inplace` ——
   `_get_accounts` 对旧结构返回的是新建 dict，改它不影响原数据，必须专门处理）
3. `_find_user_by_token` 双方都做规范化比较
4. `_merge_user_account` 合并时按规范化 token 去重，并保留目标记录的昵称/状态

**关键 bug**：`_INVISIBLE_CHARS` 原本在源码里**直接写不可见字符**，
编辑过程中被规范化工具改掉，导致零宽空格根本清不掉。
改为**纯 ASCII 转义写法**（`"\u200b\u200c\u200d"` 等），实测 18 种隐形字符全部清理成功。

**验证**：新增 5 组存量清理专项测试（脏 token 重复可检出 / 规范化匹配 /
无重复时顺手清理脏 token / 跨平台重复合并 + 群成员同步 / 不同 token 不误合并），
**二十套测试总计 0 失败**。

### 追加：修复「重复执行同一 login」产生重复账号（真正的根因）

用户指出重复大概率来自「一个人重复执行了两次相同的 login token」。
**根因在 `_upsert_account`**：账号匹配用的是**精确比较** `acc.get("token") == token`。
若账号列表里存的是脏 token（带隐形字符），而新登录提交的是干净 token，
精确比较匹配不上 → **每次 login 都追加一个新账号** → 重复不断累积。

**修复**：`_upsert_account` 改为按**规范化后的 token** 匹配，
并把 `account["token"]` 写回规范化形式：
```python
norm = SklandPlugin._normalize_token(token)
account["token"] = norm
for acc in accounts:
    if acc.get("token") == norm:   # 原来是精确比较
        acc.update(account); break
else:
    accounts.append(account)
```

至此形成完整闭环（三层都用规范化比较）：
1. `_find_user_by_token` —— 跨用户查找
2. `_upsert_account` —— 同一用户内匹配
3. `_merge_user_account` / `skdmerge` —— 合并去重

**验证**：新增 5 组重复登录专项测试（同一人连续 login 5 次 /
每次带不同隐形字符 / 历史脏 token + 干净 token / 不同 token 保留为多账号 /
`_upsert_account` 直接调用），**二十一套测试总计 0 失败**。
