## 项目分析：astrbot_plugin_skland

通读了插件全部源码（main.py 421行 / skland_api.py 616 行），确认作用与结构：

- 本质是给 AstrBot 写的**森空岛自动签到插件**（v1.4.0，作者 Azincc），由 Rust 版Skland-Auto-Sign-In 移植而来，核心难点在设备指纹伪装 + 请求签名。
- `skland_api.py`：协议层。设备 dId 生成（RSA 加密 UUID、24 字段 DES 混淆表 tn 校验、gzip + AES-128-CBC 上报 fp-it.portal101.cn），后续按 `grant → cred → binding → attendance` 四步换取并签名调用；签名 = HMAC-SHA256 后再 MD5，方舟与终末地端点不同，终末地按 `sk-game-role` 头逐角色循环。
- `main.py`：AstrBot 调度层。5 个指令（skdhelp/skdlogin/skdlogout/skdusers/skd）+ APScheduler 每日定时签到 + KV 存储 users/groups 落库。
- 双游戏支持（明日方舟 appCode=arknights、终末地=endfield），终末地支持一人多号。

### 已发现的代码问题（未修改，仅记录待用户确认）

1. `main.py:389` 昵称回写用 `put_kv_data("users", {..., user_id: {"last_username": nickname}})`，**整体覆盖该用户记录**，会把 token、umo、last_sign 等字段全部丢掉。属严重数据丢失 bug，且与同函数末尾的`users_data[uid] = user_data` 逻辑冲突。
2. `main.py:386` `if user_id in str(users_data.get("umo"))` 判断写错，疑似应为 `str(user_data.get("umo"))`，导致昵称更新分支几乎不会正确命中。
3. `main.py` 第 407 行裸`except:` 吞掉所有异常，无日志。
4. `skland_api.py` 中 import 顺序不规范（`logger = logging.getLogger` 夹在 import 中间）；logger 用标准 logging 而非 AstrBot logger，日志不会进 AstrBot 日志系统。
5. `_conf_schema.json` 默认值与 `main.py:_init_config` 的 `put_config` 默认值冲突：auto_sign_enabled false/true、auto_sign_hour 9/1。
6. `/skd` 群聊模式对每个群成员都串行跑一次完整鉴权链（4~5 次 HTTP），人数多时很慢且请求量大。
7. token 明文存 AstrBot KV，等同密码；且 `skdlogin` 群聊拦截只提示撤回，未自动撤回消息。

`AGENTS.md` 内容是 Rust 项目的规范（cargo build 等），与实际 Python 插件不符，属于文档遗留，未清理。

## 接入 QQ 官方机器人的可行性分析（仅分析，未改代码）

### 平台能力调研结论（2026-10-20 当日核实）

QQ 官方机器人（qq_official）相比 OneBot/NapCat 的关键限制：

1. **主动推送已被官方取消**（2025-04-21 公告）。后续「残缺版」下放：群聊需群主在手机端手动开启「允许主动在群聊内发言」且**默认关闭**；单聊仅在用户先发过消息后，按当天/1-3天/3-7天/7-30天四个周期各下发 1 条召回消息，**总计 4 条封顶**。
2. **被动回复窗口 5 分钟**，每条消息最多回复 5 次。
3. **群聊必须 @ 机器人**才能触发指令。
4. **AstrBot 适配器限制**：qq_official 只实现了 `on_group_at_message_create`，**没有实现 `on_group_message_create`**，即使 QQ 推送了全量群消息 AstrBot 也会静默丢弃（GitHub issue #8131，2026-05 仍未修复）。需@机器人触发。
5. 沙箱环境最多 20 人；正式环境需 IP 白名单；**只能被加到自己为群主的群**。
6. 用户 ID 体系不同：单聊用 openid（非 QQ 号），群用 group_openid，**与 OneBot 的 QQ 号不通用**。

### 结论

插件**核心卖点「每日定时私发签到结果」在 QQ 官方平台上不可行**，这是产品级冲突，不是改几行代码能绕过的。

### 推荐方案：推送模型 → 拉取模型

- 定时任务仍按时执行签到，但**结果只落库不推送**（`user_data["last_result"]`）
- 用户主动发 `/skd` 时读库渲染，附「上次签到时间」
- 群聊汇总改为可选增强：群主开启主动发言开关后，每日群内播报一次小结，失败静默降级
- 额外收益：顺带解决原 `/skd` 群聊每次都跑完整鉴权链的性能问题

### 代码改造点定位

- `main.py:180 _send_private_message` — 整块需重设计（阻塞点）
- `main.py:232 / 286 / 339 / 362` 的 `getattr(event.message_obj, "group_id", None)` — 应改用 `@filter.event_message_type(...)` 装饰器
- `main.py:357 skd` 群聊分支 — 遍历逻辑重写，groups key 需按 platform_name 隔离
- `main.py:269` 存 `umo` 当推送地址 — 官方平台下语义失效
- `main.py:241` users 主键 — openid 与 QQ 号不通用，同一用户跨平台会分裂成两条记录，token 需支持多平台绑定
- `skland_api.py` — **完全不用改**，签到走森空岛接口与 QQ 平台无关

## 实际实施：双平台自适应改造（v1.4.0 → v1.5.0）

用户确认场景为 **OneBot → QQ 官方机器人 迁移**。已按平台自适应方案完成改造，同一插件两边都能跑。

### 设计决策

1. **平台探测**：`_detect_platform()` 优先检查 `message_obj.raw_message` 的类型模块是否含 `botpy`（不受用户自定义平台 ID 影响），回退到 `get_platform_name()` 字符串匹配。
2. **能力表**：`PLATFORM_CAPABILITY` 字典集中描述各平台的 `can_push_private` / `can_push_group` / `need_at_in_group`。
3. **推送模式开关** `push_mode`：`auto`（按平台自动判断，默认）/ `private`（强制推送）/ `pull`（强制仅落库）。
4. **拉取模型**：签到结果始终写入 `user_data["last_result"]`（含 time/text/ok），私聊 `/skd` 直接读库渲染，零额外请求。
5. **多平台共存**：新增 `umo_by_platform` 字段存 `{平台: umo}`，同一用户双平台各绑一次后任一平台登出不互相影响；`_resolve_user_key()` 通过 `alias.uid` 归一 openid 与 QQ 号分裂。
6. **群记录隔离**：群键改为 `{平台}:{group_id}`，避免 openid 与 QQ 群号冲突；`_migrate_storage()` 自动迁移 v1.4.0 的旧 list 结构。

### 顺带修复的 v1.4.0 缺陷

- **数据丢失 bug**（`main.py:389`）：原代码更新昵称时整体覆盖用户记录，会丢掉 token/umo/last_sign。现改为复用既有记录仅更新目标字段。
- `if user_id in str(users_data.get("umo"))` 判断对象写错 → 已移除该失效分支。
- 裸 `except:` → 改为捕获并记日志。
- `_conf_schema.json` 与 `put_config` 默认值冲突（开关 false/true、时间 9/1）→ 已统一。
- `skland_api.py` logger 改接 AstrBot（失败回退标准库），import 顺序规范化，签到响应日志降级为 debug。
